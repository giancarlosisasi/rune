# rune inspect

```
rune inspect <name> [--root]
```

Prints exactly what `rune run <name>` would execute, and where every part of it came from. It
spawns nothing — not the command, and not the shell. The shell is consulted for its name only,
because that is what decides how arguments are quoted.

```
$ cd packages/legacy && rune inspect test
test

command      vitest run --reporter=dot --maxWorkers=1
directory    packages/legacy
environment  NODE_ENV=test                 this script's `env`
             DATABASE_URL=postgres://ci    the process environment
ignored      `DATABASE_URL` on line 4 of `.env.test` was ignored: the process environment already sets it
env files    `.env.test`  3 assignments used, 1 ignored

resolved through
  rune.config.ts                  test  runs `vitest run --reporter=dot`, sets NODE_ENV
  packages/legacy/rune.config.ts  test  appends `--maxWorkers=1`
```

The report opens with the script name, then a labelled block, then the members when the script has
any, then the chain that produced it.

## The labelled block

A label appears only when the script gave it something to say. A script with no environment of its
own prints no `environment` line at all, so the lines that are there are the decisions the config
made.

| Label | Content |
| --- | --- |
| `command` | The final string, after inheritance, per-OS selection and argument quoting |
| `runs rune` | Printed when the command starts Rune again, and says when the script it starts is this same one |
| `runs` | A serial group's members, in order, joined by arrows |
| `all at once` | A parallel group's members |
| `succeeds if` | What the group's success policy means, said rather than named |
| `on failure` | Printed when the group sets `continueOnError` |
| `runs first` | The script's `dependsOn` chain |
| `lifecycle` | One line per declared timeout, retry, kill signal and kill timeout |
| `directory` | The working directory, relative to the config root |
| `environment` | Every variable the config had something to say about, and what put it there |
| `ignored` | Assignments that did not take effect, and why |
| `env files` | Each file that took part, with how much of it was used |

`environment` is the config's own delta. `PATH` and the `RUNE_` variables are not listed: Rune
sets them for every script, so printing them would bury the one line that was a choice.

Every value names its source, because the source is what decides the answer. A value from an
`envFile` loses to the real environment and a value from a script's own `env` map beats it — the
same variable at the same value, from opposite ends of the precedence rule. Where the environment
won, the row shows the value the child will actually get, beside the assignment that lost.

A value is escaped before it is printed, so one spanning lines stays on one row, and a value too
long for the row is cut with its true length stated. The child still receives the exact bytes.

### Commands that run Rune

A command that runs Rune looks like any other command, and the only thing that separates a useful
nested call from a script that calls itself without end is which name follows:

```
$ rune inspect loop
loop

command      rune run loop
runs rune    starts rune again, on this same script
             a script whose command runs itself calls itself without end
directory    .

resolved through
  rune.config.ts  loop  runs `rune run loop`
```

Rune reads the leading word of the command and nothing else. A command that begins with an operator
or a variable is left alone, and the report carries no such line.

## Chains

Every step that contributed appears under `resolved through`, base first, each naming the config
it came from and what it put in:

```
$ rune inspect test:ci
test:ci

command      vitest run --reporter=dot --coverage --reporter=junit
directory    .

resolved through
  rune.config.ts  test           runs `vitest run --reporter=dot`
  rune.config.ts  test:coverage  appends `--coverage`
  rune.config.ts  test:ci        appends `--reporter=junit`
```

A step names what that level declared — the arguments it appended, the variables it set, the
prerequisites and working directory it chose, the file it named, the lifecycle keys it wrote. A
level that did not change the command does not claim to run it.

### Configs that took no part

Exactly two configs resolve a name: the nearest one and the root. A third in between is never
read, not even parsed, so nothing else can tell you it is being ignored. `resolved through` names
it:

```
$ cd apps/api && rune inspect lint
lint

command      biome lint .
directory    apps/api

resolved through
  rune.config.ts       lint  runs `biome lint .`
  apps/rune.config.ts        took no part — only the nearest config and the root are read
```

## Groups

A group is explained to the bottom in one invocation. Each member carries the command it resolves
to, its kind when it is a group of its own, and whatever it declared about running:

```
$ rune inspect ci
ci

runs         check → build → test
directory    .

members
  check        runs lint, typecheck, format at once
               on failure   lets the others finish, then reports
    lint       biome lint .
    typecheck  tsc --noEmit
    format     biome format .
  build        tsc -b
               runs first   clean:all
               lifecycle    ends the whole tree after 600000 ms
  test         vitest run
               environment  NODE_ENV=test  this script's `env`

resolved through
  rune.config.ts  ci  runs check, build, test
```

There is no depth limit and no flag: every level is rendered. A member appears once for every time
it runs, because Rune orders scripts and does not deduplicate work.

A member repeats nothing the group already said. Its directory is printed only when it differs
from the script you asked about, and a parallel member states its success policy only when it is
not the default.

## Lifecycle

Declared timeouts and retries print as what they do:

```
$ rune inspect e2e
e2e

command      playwright test
lifecycle    ends the whole tree after 600000 ms
             retries 2 more times on failure, waiting 2^attempt seconds between them
directory    .

resolved through
  rune.config.ts  e2e  runs `playwright test`
```

Defaults are left out. A report that printed `SIGTERM after 5000 ms` for every script would hide
the one line that was a decision.

## Flags

`--root` inspects the root definition, ignoring anything a package narrowed. A name that is missing
under the flag says which scope was searched, and names the config that does define it when
dropping the flag would find one.

`rune inspect` takes no pass-through arguments. Use `rune run` for that.

## Exit code

0 when the script resolves. 1 when the name is unknown, with the same suggestion and listing
`rune run` produces.
